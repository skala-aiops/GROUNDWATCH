# GroundWatch 공공기관 서비스 검토와 정리 설계

2026년 10월 7일 기준입니다. 현재 코드·화면, 통합가이드, 기존 사업기획서를 대조한 조사 결과와 후속 수정 상태입니다. 아래 전수 분류의 현재 요소는 수정 전 기준선이며, 반영 결과는 마지막 절에 구분합니다. 팀원이 구현 흐름을 이해하는 설명은 [교수님 원본과 현재 로직 비교](team-logic-guide.md)를 함께 읽습니다.

현재 가장 큰 문제는 화면의 양보다 **모델 예측 오차를 현장 위험과 연결하는 표현**, **자료가 없는 상태를 이상 없음처럼 보이게 하는 표시**, **기관 담당자 업무와 개발·시연 도구가 섞인 구성**입니다. 먼저 이 의미를 바로잡고, 과제에서 증명해야 할 기능은 운영자 화면과 시연으로 옮기는 것이 안전합니다.

## 구매자와 서비스 범위

직접 공공기관에 판매하면 구매 관계는 B2G입니다. 지하안전 업무를 수행하는 민간 용역사가 구매하면 B2B입니다. 이번 설계는 사용자의 최신 지시에 따라 공공기관 담당자를 주 사용자로 둡니다. 다만 기존 팀 지침의 B2B 필수 조건과 충돌하므로, 과제 제출에서 B2G가 인정된다고 단정하지 않습니다. 기관 사용자와 민간 구매자의 관계를 억지로 만들어서도 안 됩니다.

서울시의 실제 「지반침하 관측망시스템 개발용역」 사전규격은 관측망 관리·자료 연계·이상 알림·업무 이력·권한 관리를 다룹니다. 이는 해당 업무의 실제 발주 사례입니다. 우리 서비스 구매 의사나 지하수 모델의 현장 효용을 증명하지는 않습니다. 해당 문서는 사전규격이므로 최종 요구사항과도 구분합니다. [서울시 공고](https://www.seoul.go.kr/news/news_tender.do?nttNo=457238)

공고에 첨부된 제안요청서의 SFR004~007은 계측자료 연계, 지반침하 변화와 관련 자료, 알림·처리 이력 등을 다룹니다. SFR010~011은 사용자 중심 화면과 권한·감사 기록을 다룹니다. 지반침하 계측망과 기존 시스템 연계 사업이므로 현재의 지하수·ASOS 자료만으로 이를 충족한다고 설명하면 안 됩니다. 해당 기관의 내부 인프라와 보안 요구도 우리 서비스에 그대로 일반화하지 않습니다. [사전규격 첨부 자료](https://seoulboard.seoul.go.kr/comm/getFile?srvcId=BBSTY1&upperNo=457238&fileTy=ATTACH&fileNo=1&bbsNo=163)

현재 정직하게 설명할 수 있는 범위는 **관측소별 일별 지하수 자료와 예측 모델의 품질을 확인하는 과제용 운영 시제품**입니다. 현장 점검 순위 추천은 검증 전 가설입니다. 실제 판매 전에는 기관 담당자가 기존 관측 시스템에서 해결하지 못하는 업무, 필요한 결과물, 점검 결정에 사용할 근거를 확인해야 합니다.

| 사용자 | 필요한 판단 | 기본 화면에서 필요한 정보 |
| --- | --- | --- |
| 기관 업무 담당자 | 어떤 관측소 자료를 확인해야 하는가 | 관측소, 자료 날짜, 수집 상태, 실제 관측·예측, 확인 사유 |
| 기관 책임자 | 서비스 결과를 신뢰하고 업무에 사용할 수 있는가 | 적용 범위, 자료 누락, 처리 이력, 검증된 성능과 한계 |
| 서비스 운영자 | 자료·모델 장애를 어떻게 복구하는가 | 실패 작업, 오류 원인, 재시도, 모델 교체·복귀 이력 |
| 발표 평가자 | AIOps 루프가 실제로 동작하는가 | 정상·변화 시나리오, 감지·재학습·평가·교체·실패 유지 증거 |

기관 담당자 화면에 개발자 도구를 많이 보여주는 것으로 구매 가치를 대신할 수 없습니다. 반대로 기관에 필요할 법한 기능을 전부 과제에 추가하는 것도 피해야 합니다.

| 현재·재생 전환 중 상세 응답 | 늦게 도착한 이전 응답이 혼합될 가능성 | 관측소뿐 아니라 모드·자료·기간까지 요청 식별에 포함 |
| 숨겨진 API 문서 링크 | 일반 사용자 기능과 개발 문서 혼합 | 운영자·팀 개발 메뉴로 이동 |

정보의 위계와 다음 행동이 드러나는 목록, 짧고 정확한 상태 문구를 사용합니다. KRDS는 이 방향을 검토하는 공식 참고이며, 디자인 시스템 전체 도입을 이번 과제 필수로 확대하지 않습니다. [구조화 목록](https://www.krds.go.kr/html/site/component/component_04_01.html), [배지](https://www.krds.go.kr/html/site/component/component_04_06.html)

## 세 화면의 역할과 상태 설계

기본 메뉴는 관측소 현황, 관측소 상세, 운영 관리로 유지할 수 있습니다. 이름보다 역할을 분리하는 것이 먼저입니다.

관측소 현황에는 관측소 이름, 마지막 관측일, 자료 준비 상태, 예측 대상일, 예측값, 확인 사유를 둡니다. 전체 관측망을 다루지 않으므로 선정 25개 관측소라는 범위를 표시합니다. 현재 자료가 없을 때 과거 예측을 오늘 결과로 자동 대체하지 않습니다.

상세에는 실제 관측과 예측, 강수량, 날짜·단위, 확인 사유와 근거를 둡니다. 모델 버전·출처·수집 시각은 확인 가능한 보조 정보로 둡니다. 기관의 실제 확인·처리 업무는 현재 구현된 모델 이벤트 확인과 별개입니다.

운영 관리에는 최신 수집 실패와 모델 평가 알림, 필요한 조치를 먼저 둡니다. 학습·자료 등록·복귀·진단은 운영자 상세 기능입니다. 과거 재생과 모의 변화는 명확한 시연 영역으로 분리합니다. 현재 서버에는 사용자별 권한 검증이 없어 실제 외부 제공 전에 조회·변경 권한을 구현해야 합니다.

상태는 다음 네 가지를 독립적으로 표현해야 합니다.

1. 자료 상태: 매핑 검증 필요 / 자료 부족 / 지연 / 사용 가능.
2. 예측 상태: 모델 준비 필요 / 예측 대기 / 예측 발행 / 실패.
3. 모델 평가: 정답 대기 / 평가 자료 부족 / 기준 충족 / 오차 확인 필요.
4. 업무 처리: 실제 담당자·대상·처리 기록이 있을 때만 미확인 / 확인 중 / 처리 완료.

수정 전 `live_observations.py`의 예측 응답은 저장 예측과 입력 스냅샷이 일치하면 `NORMAL`을 부여합니다. 이는 최신 오차 평가까지 정상이라는 보장이 아닙니다. 또한 화면은 없는 현장 상태를 ‘없음’으로 표시합니다. 후속 수정에서는 이 두 연결을 분리하고 평가 대기를 독립 표시했습니다.

## 실제 판매 전에 남은 검증과 과제 범위

현재 API 인증·응답 확인과 실제 예측 운영은 다른 상태입니다. 이번 검토 기준 현재 API 경로는 승인된 관측소 매핑과 입력 자료가 준비되지 않아 25개 예측이 준비된 상태가 아닙니다. 과거 자료 25개 모델 결과를 실운영 준비도로 설명하면 안 됩니다. 근거는 `../evidence/api-transition-verification.json`, `api-source-readiness.json`과 관련 실행 기록입니다.

판매 전에 필요한 핵심 검증은 자료 식별·단위·수집 안정성, 단순 기준 모델 대비 예측 효용, 업무 담당자의 실제 활용 가능성, 사용자 권한과 감사 기록, 납품 환경·운영 책임입니다. 센서·GPR·공간정보 연계나 알림 채널은 해당 기관의 구매 요구가 확인됐을 때 범위를 정합니다. 특정 발주서의 모든 기능을 이번 과제에 추가하지 않습니다.

교수님 원본 README에는 ‘학습 목적으로만 사용’ 안내가 있습니다. 과제에서 활용하는 것과 상용 제품에 제공 코드를 사용하는 것은 구분해야 하며 상용 사용 범위를 확인해야 합니다. API 자료 이용 조건과 제공 코드 사용 조건도 서로 다릅니다. 원본을 삭제하거나 출처를 숨겨 해결할 문제가 아닙니다.

## 수정 순서와 안전한 제거 기준

1. 잘못된 정상·위험·현장 표현과 상태 계약을 먼저 고칩니다. 준비 안 된 자료가 정상으로 표시되지 않는 것이 완료 기준입니다.
2. 현재·과거·모의 자료를 분리하고 날짜·단위를 명시합니다. 같은 화면에 다른 모드 응답이 섞이지 않아야 합니다.
3. 운영자 도구와 시연 도구를 이동합니다. 과제 필수 루프·업로드 API·실행 증거는 남겨야 합니다.
4. 팀 기획서·계약·운영 설명을 같은 범위로 맞춥니다. 실측·목표·가설을 구분합니다.
5. 원천 매핑과 실제 예측 준비를 검증합니다. 화면이 깔끔해진 것을 실제 서비스 준비 완료로 처리하지 않습니다.
6. 기관 PoC에서 확인된 업무만 추가합니다. 권한·보안·처리 결과 등 실제 제공 조건을 검증합니다.

화면 요소를 없애기 전 HTML 요소와 JS 이벤트, API 호출, 시연 절차, 제출 증빙의 연결을 확인합니다. 버튼 이동 후에는 정상·자료 없음·실패·과거 재생에서 각각 결과를 확인합니다. 재학습 실패 시 기존 모델 유지, 복귀 후 실제 예측 버전, 현재·재생 격리를 확인합니다. 원본 소스·자료·모델·로그·Git 이력·필수 제출 증거는 삭제하지 않습니다.

예상 수정 대상은 `serving_app/static/index.html`, `groundwatch.js`, `external-data.js`, `groundwatch.css`, 상태 응답을 만드는 `live_observations.py`·`groundwater_api.py`, 그리고 위 문서들입니다. 후속 구현에서 화면 문구·평가 상태 분리·상세 요청 범위 검사·운영 도구 접기·조회 주기 조정·문서 보관과 TODO 축소를 반영했습니다. 원천 API 검증·권한·실제 업무 효과는 아직 완료되지 않았습니다.
