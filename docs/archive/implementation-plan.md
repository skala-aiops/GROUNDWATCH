# GroundWatch 팀 구현 설계 및 과제 기준 사전 점검

2026-10-07 API 운영 전환의 최신 변경 기준은 [재설계](../api-transition-redesign.md)와 [현재 계약](../contracts.md)입니다. 아래 기존 과거25구 설계·평가 정책은 보존하며, 공급·DB·live 날짜·모델 입력 버전은 새 경로에서 분리했습니다. 실제 API 매핑은 미승인 상태이고 today 예측 활성화는 완료되지 않았습니다.

작성 기준: 2026-10-07. 구현을 진행하며 확인한 데이터 조건을 반영했습니다. 완료 기준과 실제 실행 결과는 구분하며, 최종 실행 상태는 `../evidence/README.md`를 따릅니다.

## 1. 확정 목표와 변경 범위

서울 25개 구마다 대표 관측소를 하나씩 고정하고, 각 관측소의 최근 20일 지하수위와 강수량으로 다음 날 지하수위를 예측합니다. 전체 25개 구 결과를 같은 기준일로 조회하고, 예측 오차 증가를 감지하면 재학습·평가·모델 교체 또는 기존 모델 유지를 수행합니다.

관측소 한 곳의 값은 구 전체의 평균이나 싱크홀 발생 확률이 아닙니다. 화면은 대표 관측소의 환경 변화와 모델 품질을 구분하여 보여줍니다. 팀 과제의 B2B 조건을 따라 구매자는 건설사·환경안전 관리 기업, 사용자는 환경·안전 담당자로 둡니다. 기획서의 지자체 수요는 B2G 확장 대상으로 유지합니다. 공개 관측소 자료만으로 특정 공사 현장의 안전을 판단했다고 주장하지 않습니다. 담당자가 우선 확인할 관측소를 찾는 업무를 지원하고, 점검 시간 절감은 실제 비교 실험 전까지 가설로 남깁니다.

기획서의 최초 범위인 관측소 1곳·모의 데이터는 사용자 최신 지시에 따라 25개 구·실제 제공 CSV 기반으로 확장합니다. 실시간 외부 API 수집, 지도, 앙상블, 위험 확률 추정은 필수 범위에 추가하지 않습니다. 기존 FastAPI·정적 화면·단일 Docker 컨테이너·로컬 MLflow 구조를 유지합니다.

읽기 전용 점검 대상은 Downloads의 `관측소_측정소_측정지역_매핑표_UTF8_BOM.csv`, `서울시_보조지하수_강수량_통합데이터_UTF8_BOM.csv`, `서울시_보조지하수_강수량_통합데이터_결측치제거_UTF8_BOM.csv`입니다.

공통 날짜 검사는 관측종료 이름을 제외하고, 동일 관측소·일자의 수위/강수 충돌을 격리한 조건입니다. 단위 확인 전 부호로 제거하지 않았습니다. 이는 제공 파일 점검 결과이며 공식 원천 전체의 데이터 부재를 의미하지 않습니다.

### 데이터 계약과 복구 절차

1. 원본은 수정하지 않고 파일 해시·출처·수령일을 기록합니다. 대용량 원본과 모델은 Git에 무조건 추가하지 않습니다.
2. 공식 관측공 코드·측정 기준·단위를 확인합니다. 같은 이름에 다른 관측공이나 측정 시간이 섞였다면 식별자를 분리합니다. 확인 전 이름만으로 평균을 내거나 마지막 행을 선택하지 않습니다.
3. 날짜를 달력 일자로 정규화하고 잘못된 날짜·미래 일자·비수치·무한값을 격리합니다. BOM은 `utf-8-sig`로 읽습니다.
4. 수위 원본에 공식 강수 자료를 다시 결합합니다. 강수 측정소 코드, 유효 기간과 위치 근거를 기록합니다. 강수 결측은 자동 0으로 만들지 않습니다. 공식 자료가 무강수를 0으로 정의한 경우에만 0을 사용합니다.
5. 팀이 공식 CSV를 한 번 내려받아 가져오는 방식으로 충분합니다. API 키가 필요한 실시간 수집기는 필수 구현에서 제외합니다. 출처·라이선스·단위를 확인합니다.
6. 정규 자료 열은 `station_id, district_code, date, groundwater_level, rainfall_mm, level_unit`이며 데이터 버전은 파일 해시와 manifest로 관리합니다. 원천 식별자와 변환 근거를 추적할 수 있게 보존합니다.
7. 구별 후보를 최신성·연속 구간·충돌률·원천 식별 가능성으로 선정합니다. 테스트 점수가 높은 관측소를 사후 선택하지 않습니다. 사용자가 위임한 공개 원천 조사·선정 근거로 정확히 25행의 대표 관측소 manifest와 mapping_version을 고정합니다. 자동 대체하지 않습니다.

첫 단계 완료 기준은 단위와 식별자 확인, 충돌 처리 근거, 대표 25곳 확정, 학습/평가/시연 기간 확보입니다. 구현 중 공식 관측소 66곳을 조회하여 단위 `gl.-m`·공식 ID와 원천 강수 `mm`를 확인했습니다. 사용자의 조사·선정 위임에 따라 대표 25곳과 실제 52,591행을 `data/representatives.json`, `data/groundwater_observations.csv`로 고정했습니다. 원본 한글 CSV의 부호를 추정 변환하지 않고 공식 화면의 실제 값을 다시 확보했습니다. 출처·공공누리 제1유형과 원본 해시는 `data/README.md`, `evidence/frozen-data-manifest.json`에 남깁니다.

현재 자료는 오늘까지의 실시간 자료가 아닙니다. 최초 서비스와 시연은 확보된 과거 공통 기간의 `historical_replay` 모드로 구성합니다. `as_of` 관측 기준일과 실제 실행 시각을 함께 표시합니다. 최신 조회 모드는 자료 지연을 명시하고, 서로 다른 과거 날짜 예측을 같은 오늘의 순위로 비교하지 않습니다.

## 4. 학습과 평가

구별 대표 관측소마다 독립 LSTM·scaler·모델 버전을 둡니다. 모델 수는 25개입니다. 입력은 이전 20개 연속 달력일의 `[지하수위, 강수량]`, 정답은 다음 달력일 지하수위입니다. 정답 날짜의 실제 강수량을 미리 넣지 않습니다. 출력은 확인된 원천 수위 단위를 사용합니다.

기본 구조는 LSTM 32→32→Dense 16→출력 1입니다. 실제 첫 학습의 절대수위 모델은 25개 중 8개만 초기 게이트를 통과하여, 마지막 관측값에 LSTM이 학습한 변화량을 더하는 residual 구조를 추가했습니다. seed 42, 최대 100 epoch, batch 32, shuffle=False, validation loss 기반 patience 10, residual 초기 learning rate 0.0001을 사용합니다. 게이트를 낮추지 않으며 구조 선택은 검증 지표를 근거로 합니다. 반복 개발 중 잠금 테스트 지표도 기록되므로 최종 테스트를 완전히 처음 보는 외부 평가로 과장하지 않습니다.

정답 날짜 기준으로 과거→미래 순서의 train/validation/test/replay를 분리합니다. 최초의 ‘25개 구 공통 연속 410일’은 교수자 필수가 아닌 설계 가정이었으며 공식 자료가 충족하지 않아 수정했습니다. 실제 구현은 각 입력 20일과 정답 1일의 연속성을 검사하고, 공백을 가로지르는 창을 제외합니다. 구별 과거 유효 학습 정답은 최소 180개, 최대 최근 730개입니다. 검증·테스트 정답은 각각 연속 60일, 공통 재생 정답은 2023-12-20~2024-03-18의 연속 90일입니다. 학습 창 사이에는 공백이 있을 수 있지만 한 입력 안에서는 날짜를 이어 붙이지 않습니다. 구별 실제 분할 날짜와 scaler fit 범위를 저장하고 미래 평가 자료를 학습에 넣지 않습니다.

scaler는 각 구의 train에만 fit하고 해당 모델과 묶어 저장합니다. 검증으로 설정을 선택하고 test는 최종 보고용으로 잠급니다. 운영 중 test를 반복 게이트에 쓰지 않습니다. 매 구마다 ‘내일도 오늘 수위와 같다’는 persistence 기준 모델과 동일 날짜의 RMSE·MAE·표본 수를 비교합니다. 25개 구별 지표와 전체 macro 평균, 예측 가능 구 수를 함께 보고합니다.

초기 게이트 제안은 유한한 예측·정상 로딩·계약 검증과 `validation RMSE ≤ persistence validation RMSE × 1.10`입니다. 10% 허용치는 설계 초깃값이며 실제 업무 허용 오차가 아닙니다. 실패 모델은 미준비 상태로 표시하고 원인을 분석합니다. 25개 숫자를 채우려고 게이트를 몰래 낮추지 않습니다. 달러 기준 RMSE 4를 수위 기준으로 재사용하지 않습니다.

## 5. 감지→재학습→평가→교체

예측 시 구·관측소·모델 버전·기준일·정답 예정일·예측값·자료 버전을 영속 저장합니다. 실제 다음 날 관측값이 도착한 뒤에만 잔차를 계산합니다. 같은 정답을 중복 반영하지 않습니다. 구별·모델 버전별 최근 21개 연속 정답 날짜의 RMSE를 계산하며, 정답 부족·입력 결측은 모델 품질 알림과 별도로 표시합니다.

첫 감지 설정은 검증 구간 21일 rolling RMSE의 P95 × 1.5를 두 번 연속 초과하는 조건입니다. 배수와 횟수는 조정 가능한 설계값이며 현장 위험 임계값이 아닙니다. 오차 상승은 성능 저하 신호이며 입력 분포 변화 원인을 입증한 것으로 표현하지 않습니다. 수신자는 팀이 정한 운영 담당자이고, MVP에서는 화면·영속 이벤트 로그로 알립니다.

상태는 `NORMAL → WARN → QUEUED → TRAINING → EVALUATING → PROMOTED / REJECTED / FAILED`입니다. 한 구에 진행 중인 후보는 하나, 전체 동시 학습 작업도 하나로 제한합니다. 재학습은 최소 21개 새 정답 확보 후 다시 허용하고, 재생 모드의 쿨다운은 재생 시계를 사용합니다.

1. 해당 시나리오·구의 최신 연속 41일로 20일 입력 문맥과 21개 정답을 구성합니다. 임의 업로드 파일의 수정 시각으로 학습 자료를 선택하지 않습니다.
2. 현재 champion 가중치와 고정 scaler로 fine-tuning합니다. 시작 설정은 10 epoch, learning rate 0.0001입니다.
3. 41일의 작은 내부 holdout만으로 교체하지 않습니다. 후보 생성 이후의 새 정답 30일 동안 후보와 champion을 같은 입력으로 shadow 평가합니다. 정답이 아직 없으면 평가 대기이며 기존 모델을 계속 제공합니다.
4. 제안 교체 조건은 새 30일 후보 RMSE가 champion의 95% 이하이고, 별도 과거 검증 구간 오차가 기존 대비 110% 이내이며, 로딩·입력 계약·유한값 검사를 통과하는 것입니다. 5% 개선·10% 회귀 한도는 설계값으로 기록합니다. 과거 검증은 회귀 방지용이며 새 일반화 성능으로 주장하지 않습니다.
5. 후보를 먼저 로딩·smoke test한 뒤 구별 lock 안에서 champion alias와 메모리 cache를 교체합니다. 실패하면 이전 alias/cache를 복구하고 실패 이벤트를 남깁니다. 재시작 시 registry와 cache를 대조합니다.
6. 새 버전의 실제 API 예측을 확인해야 교체 완료입니다. MLflow 등록·alias 변경 화면만으로 서빙 교체를 완료 처리하지 않습니다. 교체 후 이전 버전 오차 창을 섞지 않고 21개 새 정답을 기다립니다.

현장 확인 이벤트는 별도 `OPEN → ACKNOWLEDGED → RESOLVED`로 관리합니다. 모델 품질이 좋아졌다고 현장 이상을 자동 해제하지 않습니다. 수위 변화의 안전 기준은 확인되지 않았으므로 위험 등급·대피 판단·위험 확률을 만들지 않습니다.

## 6. 실행 구조와 영속성

```text
원본 CSV → 검증/격리 → 수위·강수 결합 → 대표 25곳/자료 버전
                                       ↓
                           구별 시간 분리 학습·평가
                                       ↓
                       MLflow 모델+scaler+metadata / champion
                                       ↓
브라우저 ← FastAPI API ← 구별 모델 cache → 예측·정답·오차 기록
                                       ↓
                              감지·이벤트·영속 작업 큐
                                       ↓
                         단일 학습 worker → 후보 평가 → 교체/유지
```

Docker Compose의 단일 서비스 안에서 FastAPI 1 worker와 학습용 worker 프로세스를 실행합니다. 무거운 TensorFlow 학습은 HTTP 요청 안에서 실행하지 않습니다. 작업은 SQLite에 저장하고 202와 job_id를 즉시 반환합니다. 재시작 때 실행 중이던 작업은 interrupted로 기록하고 명시적 재시도 대상으로 둡니다. 숨겨진 중복 학습을 방지합니다.

MLflow SQLite와 서비스 메타데이터 SQLite는 분리합니다. 볼륨에는 tracking/artifacts/models/datasets/metadata/logs를 보존합니다. 모델 이름은 `GroundWatch_<namespace>_<district_code>`, 실제 서빙 식별자는 registry version과 `champion` alias입니다. 모델 묶음에는 scaler, 열 순서, 단위, station/mapping/dataset version, 학습 종료일, 지표를 포함합니다. HAIC 샘플 모델로 자동 대체하지 않습니다. 준비 전에는 data_required/model_not_ready를 표시합니다.

실행 명령은 저장소 루트의 `docker compose up --build` 하나를 유지합니다. 최초 실행은 화면·업로드 API를 제공하고, 합법적으로 공유 가능한 확정 데이터가 포함된 경우에만 초기 학습을 작업으로 등록합니다. 데이터나 단위가 없는데 예측 준비 완료로 표시하지 않습니다. 기존 개인 실습 컨테이너와 볼륨은 건드리지 않습니다.

## 7. API 계약

현재 구현 계약의 상세는 `docs/contracts.md`입니다. 날짜는 ISO 8601, 수치는 JSON number, 누락 예측은 null과 사유로 반환합니다.

| Method / 경로 | 동작 |
| --- | --- |
| GET /health/live, /health/ready | 프로세스 상태 / 자료·25개 모델 준비 수 구분 |
| POST /api/v1/datasets | 정규 CSV와 manifest JSON 업로드, 검증 작업 202 |
| GET /api/v1/districts | 고정 대표 관측소 25곳과 mapping_version |
| GET /api/v1/forecasts?as_of=YYYY-MM-DD&mode=historical_replay | 같은 기준일 전체 25개 결과 |
| GET /api/v1/districts/{code}/history | 실측·예측·강수·오차 시계열 |
| POST /api/v1/jobs/train | 자료 버전과 구를 명시한 학습 작업 |
| GET /api/v1/jobs/{id} | 상태·실패 사유·지표·실제 모델 버전 |
| POST /api/v1/replays, /replays/{id}/advance | 격리된 재생 생성·시계 진행 작업 |
| GET /api/v1/models, /events | 모델·게이트 이력과 운영 이벤트 |
| POST /api/v1/events/{id}/ack, /resolve | 담당자의 확인·해제와 사유 기록 |
| POST /api/v1/models/{code}/rollback | 이전 검증 버전 복구·감사 로그 |

예측 행은 district_code, station_id, observed_date, forecast_date, prediction, unit, model_version, dataset_version, mapping_version, quality_status, inspection_status, mode, replay_id, generated_at을 포함합니다. 정상 전체 조회는 항상 25행이고, 최종 완료 조건은 같은 기준일 25행 모두 실제 모델 예측값을 갖는 것입니다. 미준비는 숫자를 만들지 않습니다.

잘못된 날짜·열·수치·입력 길이·구 코드·연속성은 422와 구체적 필드 오류를 제공합니다. 진행 작업 충돌은 409, 모델 미준비 개별 예측은 503으로 구분합니다. 전체 현황 조회는 200 안에 구별 준비 상태를 포함합니다. 조작 API는 로컬 시연 운영용이며 외부 공개 운영 인증 완료를 주장하지 않습니다.

## 8. 화면과 운영 목표

데스크톱 화면은 전체 현황, 구별 상세, 운영 관리 세 영역으로 구성합니다. 전체 현황은 25개 구의 대표 관측소·같은 기준일 예측·자료 지연·모델 품질·현장 확인 상태를 보여줍니다. 상세는 실측/예측 그래프, 강수 단위, 21일 RMSE와 임계값, 버전 변경 시점을 보여줍니다. 운영 관리는 업로드 검증, 작업 진행, 후보/기존 비교, 게이트 실패, 교체·롤백 이력을 실제 API에서 읽습니다.

교수자 참고 URL 172.16.10.199:8077/8088은 현재 접근되지 않아 화면을 확인하지 못했습니다. 확인되지 않은 디자인을 복제했다고 설명하지 않습니다. 현재 정적 프론트를 모듈화하고 실제 데이터를 연결합니다.

운영 목표 초안은 준비된 전체 예측 조회 p95 1초 이하, 통제된 100회 정상 요청에서 5xx 1% 미만, 잘못된 입력 422, 재시작 후 버전·이력 보존입니다. 환경·요청 조건과 함께 실측합니다. Docker 정상 실행을 클라우드 가용성이나 24시간 SLA로 표현하지 않습니다. 품질은 구별 persistence 비교와 교체 게이트로 관리합니다.

## 9. 파드 작업 경계

데이터·AI 파드는 ingestion/quality/대표 선정, 구별 features/scaler, train/evaluate, registry/cache, residual/drift/retrain을 맡습니다. 웹 파드는 요청 검증·응답 DTO·조회 API·화면·작업/이벤트 표시를 맡습니다. SQLite repository, 작업 큐, 공통 API와 Docker는 공동 계약으로 파일 담당자를 지정합니다. 팀원 이름과 병합 권한을 임의로 배정하지 않습니다.

기존 `data/`, `serving_app/`, 정적 프론트 경로를 활용하고 ingestion/quality, training, monitoring, repositories, worker 책임을 분리합니다. 폴더 재배치 자체를 목표로 삼지 않습니다. 공용 `predict.py`, model_loader, 응답 필드 변경은 선행 계약 없이 양 파드가 동시에 수정하지 않습니다.

개인 작업 → pod/web 또는 pod/aiops → dev → main의 기존 규칙을 적용하고 이슈·PR은 사용하지 않습니다. AI 요청에는 AGENTS.md와 이 계획, 확정 계약을 먼저 읽도록 지시합니다. 계획은 실행·검증을 대신하지 않습니다.

## 10. 단계별 구현·검증 순서

1. **데이터 확보:** 단위/식별자·충돌 격리·공식 강수 복구·대표 25곳·유효 학습 창 및 공통 90일 재생 기간을 검증합니다. 근거는 frozen-data-manifest와 원천 해시입니다.
2. **계약과 한 구 전체 흐름:** 실제 데이터 업로드→시간 분리 학습→MLflow→예측 200/422→정답 대조를 한 구에서 검증합니다.
3. **25개 구 확장:** 모델/scaler/cache 분리, 동일 기준일 25개 예측, 구별 RMSE/MAE와 baseline 비교, 준비 상태를 검증합니다.
4. **AIOps:** 한 구의 정상/변화/게이트 성공/실패/롤백을 검증한 뒤 다른 24개 구에 영향이 없는지 확인합니다. 정답 도착·30일 후보 평가·실제 새 버전 응답까지 확인합니다.
5. **화면·Docker:** 화면→API→실제 모델 연결, 작업 중 조회, 오류 표시, 새 프로젝트명·새 볼륨으로 최초 실행, 재시작 영속성을 검증합니다. 기존 볼륨 삭제로 시험하지 않습니다.
6. **제출:** 기획서 6항목을 실제 결과로 갱신하고 20분 이내 발표/시연을 준비합니다. PDF/발표는 렌더링 검수합니다. 공식 최신 일정은 상위 `docs/instructor-milestones.md`를 따릅니다.

핵심 테스트는 BOM·중복 충돌·날짜 공백·미래 정답 누수·train-only scaler·구별 격리·정답 미도착·중복 작업·실패 시 기존 모델 유지·cache 실제 교체·재시작·롤백입니다. 파일 생성만 확인하는 테스트보다 실제 오류 방지와 전체 흐름을 우선합니다.

시연 데이터는 원본을 보존한 별도 scenario_version으로 정상과 구조적 변화 구간을 만듭니다. 변화 크기·시작일·seed·원본 해시를 기록하고 모의 변화라고 표시합니다. 변화가 들어간 동일 시나리오를 감지·재학습·후속 정답 평가에 일관되게 사용합니다. 미래 정답을 미리 학습하지 않고 재생 시계를 하루씩 전진시킵니다. 실제 자료 시나리오와 합성 시나리오의 registry·이력을 격리합니다.

## 11. 제출 증거와 완료 판정

`proposal.md`는 공식 6항목, `operations.md`는 임계값·실패 대응 정책, `demo.md`는 실제 시연 순서, `evidence/README.md`는 실행 환경·자료 버전·모델 버전·증거 위치를 관리합니다. 동일 설명을 모든 문서에 복제하지 않습니다. `TODO.md`는 실제 결과가 있을 때만 체크합니다.

최종 증거는 25개 고정 매핑/자료 품질, 구별 평가 표본·지표, API 200/422와 Swagger, 정상 감시, WARN→재학습→평가→교체, 실패 게이트 기존 유지, 실제 응답 버전 변경, 롤백, 컨테이너 재시작, 실제 화면입니다. 제공 코드와 팀 직접 수정 및 각자 기여를 구분합니다. 모델 성능 개선과 재난 예방 효과를 동일한 성과로 쓰지 않습니다.

단위·공식 관측소 ID·대표 25곳·공통 재생 기간은 공식 자료 조사로 확보했습니다. 최초 사용자 CSV의 상충하는 측정값과 부호 변환 이력은 확인되지 않아 공식 원천 재조회 자료를 사용합니다. 원천 화면이 제공하는 강수의 기상 관측소 코드는 독립 확인되지 않았으며 실시간 수집·현장 안전 임계값·실제 업무 효과도 검증되지 않았습니다. 본 문서 저장은 과제 제출 완료를 뜻하지 않습니다.
