# 운영 기준

모델 품질 정책의 기준 문서입니다. 특정 실행 결과는 [실행 증거](../evidence/README.md)를 따릅니다. 아래 설정은 과제 운영 가설이며 지반 안전 기준이 아닙니다.


## 기동과 준비 확인

실행은 [README](../README.md)를 따릅니다. API·학습 worker·외부 수집 worker가 한 컨테이너에서 실행되고 작업은 비동기 처리합니다. SQLite·MLflow·모델·자료를 Docker 볼륨에 보존합니다.

`/health/live`는 응답 가능 여부, `/health/ready`는 기존 CSV·시연 경로의 입력과 모델 준비 여부입니다. 기본 실제 API 모델은 `/api/v1/api-observations`의 `observation_count`·`ready_count`·관측소별 상태로 확인합니다. 연속 20일 수위, 마지막 입력 날짜, 별도 모델이 필요하며 강수 결측은 아래 정책으로 처리합니다. 준비 완료와 오늘 관측 확보는 다른 상태입니다.

기본 화면은 실제 API 자료를 사용합니다. 과제 시연용 합성 확장은 기동 시 별도로 준비하며 자정 자동 갱신 scheduler는 없습니다. 기존 승인 매핑 `/live/*`와 실제 API feed는 독립 경로입니다. 수집 성공·입력 준비·모델 준비·예측 발행을 구분합니다.

## 실제 API 학습과 초기 게이트

- `api_native_masked_v1`의 구별 masked residual LSTM을 사용합니다. 입력은 연속 20일 수위·강수·강수 결측 표시이며 다음 날 실제 수위가 정답입니다. 날짜 공백을 가로지르지 않습니다.
- 최소 유효 정답 윈도우 50개가 필요합니다. 전체 유효 윈도우를 시간순으로 약 60% 학습·20% 검증·20% 시험으로 나누며 검증·시험은 각각 최소 10개입니다. 결측일 때문에 비율과 달력 기간이 같지는 않습니다.
- 강수 중앙값과 scaler는 학습 구간에서만 계산하고 이후 고정합니다. 원자료의 null·수위 원값·부호를 보존하며 모델 입력에서만 대체합니다.
- seed 42, batch 32, 최대 100 epochs, early stopping patience 10, LR 0.0001. 초기 허용은 검증 RMSE ≤ 전일 수위 유지(persistence) RMSE × 1.10입니다.
- 새 feed가 들어오면 미준비 모델만 초기 학습하고 기존 champion은 재사용해 새 입력으로 예측합니다. 매일 전체 모델을 재학습하지 않습니다. 자동 재학습은 아래 드리프트 정책을 따릅니다.

RMSE·MAE는 API 원값 단위이며 물리적 수위 단위가 검증됐다는 뜻은 아닙니다. 검증 게이트 통과가 시험 구간에서 persistence보다 우수하다는 보장은 아닙니다. 후보 평가 후 모델의 metrics에는 후속 평가·guard 지표가 표시될 수 있습니다.

## 과거 CSV·시연 모델 학습

- 구별 residual LSTM: 32 → 32 → Dense 16 → 출력 1. 연속 20일의 수위·강수로 다음 날 수위를 계산합니다.
- gap-aware 시간 분할: 최근 유효 학습 정답 최대 730개, 검증 60일, 테스트 60일, 운영 재생 90일. 공백을 가로지르지 않고 scaler는 학습 구간만 사용합니다. strict 합성 검증 분할과 혼동하지 않습니다.
- seed 42, batch 32, 최대 100 epochs, early stopping patience 10. RMSE·MAE·표본 수와 persistence 기준을 기록합니다.
- 초기 허용: 검증 RMSE ≤ persistence 검증 RMSE × 1.10. 등록과 실제 champion 사용은 다릅니다. 실패 시 기존 모델을 유지하고 없으면 미준비로 표시합니다.

RMSE는 수위와 같은 단위로 오차를 비교할 수 있고 큰 오차를 강조합니다. 수위가 음수·0을 포함하므로 백분율 오차인 WAPE를 주 평가 지표로 직접 사용하지 않습니다. 실측과 합성 구간 지표를 합쳐 현장 성능으로 설명하지 않습니다.

## 실제 API 감지 → 재학습 → 후보 평가

예측 발행 당시 정답이 없었던 대상 날짜만 저장합니다. 이후 API 수집에서 정답이 도착하면 최초 수신 정답으로 평가를 고정합니다. 과거 시험 구간 예측·중복 조회·같은 입력으로 재발행한 예측은 감지 표본을 늘리지 않습니다. 공급자가 날짜를 건너뛰어 제공하면 연속 표본 조건을 충족할 때까지 기다립니다.

| 단계 | 실제 API 정책 |
| --- | --- |
| 감지 표본 | 같은 관측소·namespace·현재 모델의 연속 정답 21일 |
| 임계값 | 초기 검증 RMSE × 1.5. 기존 시연의 rolling P95 정책과 다름 |
| 재학습 요청 | 임계값 연속 2회 초과, cooldown 21일. 후보·활성 모델 작업 중복 방지 |
| 후보 학습 | 최신 연속 41일·21개 정답, 기존 모델 복제·scaler/강수 대체값 유지, 최대 30 epochs·LR 0.0001 |
| 후속 평가 | 후보 학습 종료 다음 날부터 정확히 연속 달력 30일 정답. 빠진 날짜를 더 늦은 날짜로 대신하지 않음 |
| 교체 게이트 | 같은 30일의 후보 RMSE ≤ 기존 × 0.95, 미학습 과거 guard에서 후보 RMSE ≤ 같은 기존 모델 × 1.10 |
| guard | 부모 모델의 검증 구간 또는 상속된 guard 중 후보 학습 정답보다 앞선 최소 10개 정답 |
| 대기·탈락 | 정답 부족은 대기, 게이트 미충족은 기존 유지. 학습·로드 실패는 작업 실패와 기존 모델 유지 |

외부 worker는 60초마다 수집·학습·감시 조건을 확인합니다. 감시·재학습·평가·교체는 하나의 학습 worker에서 영속 작업으로 직렬 실행합니다. 입력 스냅샷·예측·평가·경보·작업·모델 버전을 보존하고, 재시작이나 작업 재시도로 같은 경보·후보를 중복 생성하지 않습니다. 교체 후 새 버전의 오차 창을 다시 모읍니다. 실제 운영에 새 정답이 없으면 중간 단계가 대기인 것이 정상입니다.

## 과제 시연 감지·재학습 정책

하루 진행은 t일 입력으로 t+1일 예측 저장 → t+1일 정답 공개 → 오차 평가 순서입니다. 같은 날짜의 중복 조회는 감지 표본을 늘리지 않습니다.

| 단계 | 현재 정책 |
| --- | --- |
| 감지 표본 | 동일 관측소·namespace·모델의 연속 정답 21일 |
| 임계값 | 초기 검증의 rolling 21일 RMSE P95 × 1.5, 계산 하한 1e-6 |
| 재학습 요청 | 임계값 연속 2회 초과, cooldown 21일, 최근 연속 41일 입력 확보 |
| 후보 학습 | 기존 모델 복제, 최근 41일·20일 문맥·21개 정답, scaler 유지, 10 epochs·LR 0.0001 |
| 후속 평가 | 후보 학습 뒤 새 정답 30일에서 기존과 같은 조건으로 비교 |
| 교체 게이트 | 후보 RMSE ≤ 기존 × 0.95, 과거 guard RMSE ≤ 초기 검증 × 1.10 |
| 대기·탈락 | 정답 부족은 평가 대기, 기준 미충족·날짜 공백은 기존 모델 유지 |

후보 평가 중 중복 후보를 만들지 않습니다. 모델 교체 뒤에는 새 버전의 오차 창을 다시 모읍니다. 감지는 예측 오차 증가이며 원인이나 현장 위험을 확정하지 않습니다.

## 시연·진행 표시

기본 상황은 추가 수위 변화가 없다는 뜻이며 경보가 절대 발생하지 않는다는 뜻은 아닙니다. 드리프트 시연은 별도 세션에서 첫 정답 22일째부터 수위에 +0.2를 더합니다. 예전 세션의 시작일·변화량은 보존합니다. 원본 CSV와 모델 출력·경보 결과는 조작하지 않습니다.

화면은 모델 준비·실제 처리 일수·재학습·평가 대기·실패를 표시합니다. 활성 작업의 조회는 3초, 일반 운영 조회는 30초 간격입니다. 외부 수집 주기가 아닙니다. 이미 선택한 상황은 이어서 사용하고 명시적 재시작 때만 새 기록을 만듭니다.

## 교체·복귀·장애 대응

모델을 로드하고 smoke 예측을 확인한 뒤 champion alias와 캐시를 교체합니다. 실패하면 기존 alias·캐시를 유지합니다. 실제 예측 응답의 model_version으로 새 모델 사용을 확인합니다.

이전 모델 복귀는 화면에서 사유 입력 없이 요청하며 API에는 고정 reason을 보냅니다. 실제 승격 이력이 있는 이전 검증 모델만 선택합니다. 작업 상태는 queued/running/completed/failed/interrupted이며 재기동 시 중단 작업은 자동 성공 처리하지 않습니다. 원인 확인 후 재시도하고 기존 실패 기록은 보존합니다.

모델 품질 이벤트는 OPEN → ACKNOWLEDGED → RESOLVED로 처리합니다. 외부 SMS·현장 점검 알림 발송은 구현 범위가 아닙니다. 서버 진단은 요청 ID·로그 → 준비 상태 → 작업·worker → 자료·모델 순서로 확인합니다. `/metrics/summary`의 p95 1초·5xx 비율 1%는 운영 목표이며 실측 결과는 증거에 따릅니다.

기존 `/live/*`는 승인 매핑·원천·단위·20일 입력·별도 모델을 갖춰야 하는 경로입니다. 기본 실제 API feed는 물리적 기준이 미확정인 수위를 `API 원값`으로 유지하며 다른 모델과 섞지 않습니다. 두 경로 모두 실패·부분 수집으로 정답을 만들지 않습니다. 상세 경로는 [API 계약](contracts.md)을 확인합니다.

## 실제 API 관측 feed

`GROUNDWATCH_COLLECTION_ENABLED=true`일 때 KST 10시 이후 하루 1회 자동 수집합니다. 오류가 있으면 마지막 점검 1시간 후 재시도하며 worker는 60초마다 조건을 확인합니다. 90일 자료에서 365일로 확대하는 초기 보충 수집도 허용합니다. ‘하루 1회’는 수집 배치 기준이며 서울시·기상청 페이지 요청은 여러 번입니다. 화면 수동 수집은 이 일정과 별도로 접수할 수 있습니다.

서울시 관측소·날짜 필터가 실응답에서 적용되지 않아 전체 응답을 페이지 단위로 검증해 고정 관측소 이름으로 추출합니다. 최신 유효 지하수 관측 기준 365일, 최대 120페이지이며 각 페이지는 1,000행입니다. 기상청은 날짜 범위의 ASOS 108 자료를 100행씩 요청합니다. 미래 관측을 제외하고 건수·정렬·페이지 완전성을 검사하며 실패한 원천은 이전 성공 자료와 오류 상태를 유지합니다. 모든 관측소의 365일 완전 관측을 보장하는 설정은 아닙니다.

원본 JSON·latest.json·학습/발행 입력 스냅샷·models.json은 `runtime/groundwatch/external/feed/`, 모델은 `models/api_native_masked_v1/`, 발행 예측·평가·감시·모델 작업은 팀 상태 DB에 저장합니다. 수동 수집 작업은 별도 외부 수집 DB에 있으므로 `/api-observations/collection-jobs`로 조회합니다.

2026-10-08 검증에서 최신 지하수 관측은 2026-08-31이고 25곳 예측이 준비됐습니다. 대부분 예측 대상은 2026-09-01이며 노원구는 관측 2026-07-31·예측 2026-08-01입니다. 관측일을 수집일이나 오늘로 바꾸지 않습니다. 실제 새 정답이 쌓이기 전의 대기는 서비스 실패나 드리프트 미구현을 의미하지 않습니다.
