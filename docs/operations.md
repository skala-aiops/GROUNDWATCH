# 운영 기준

모델 품질 정책의 기준 문서입니다. 특정 실행 결과는 [실행 증거](../evidence/README.md)를 따릅니다. 아래 설정은 과제 운영 가설이며 지반 안전 기준이 아닙니다.

아래 기존 학습·감지·복귀 설명은 서울 `/api/v1` 기준입니다. 추가 실험 경로 `/api/v2`의 정책과 준비 조건은 [전국 실험 경로](#전국-실험-경로-apiv2)를 따릅니다. 전국 경로의 구현이 팀 공통 계약 합의·전국 현장 검증 완료를 뜻하지 않습니다.


## 기동과 준비 확인

실행은 [README](../README.md)를 따릅니다. API·학습 worker·외부 수집 worker가 한 컨테이너에서 실행되고 작업은 비동기 처리합니다. SQLite·MLflow·모델·자료를 Docker 볼륨에 보존합니다.

`/health/live`는 응답 가능 여부, `/health/ready`는 입력과 모델의 예측 준비 여부입니다. 준비는 관측소별로 확인하며 연속 20일, 마지막 입력 날짜, 모델 존재·사용 가능 상태가 필요합니다. 프로세스가 살아 있어도 준비 부족이면 ready는 503일 수 있습니다. 현재 자료와 모델이 실제로 준비되었는지 화면의 준비 수와 실패 이유를 확인합니다.

합성 확장 자료는 기동 시 준비하며 자정 자동 갱신 scheduler는 없습니다. 외부 API의 수집 성공과 기본 화면의 합성 입력 준비는 별개입니다. 원천 상태·활성 매핑·입력·모델·예측 발행 단계를 구분하고 수집 이력만으로 실측 예측 성공이라 설명하지 않습니다.

## 운영 목표와 서비스 지표

관측·시설 유지관리 담당자가 예측을 조회할 수 있는지와 운영자가 모델 품질 저하에 대응할 수 있는지를 따로 확인합니다. 아래 수치는 과제 운영 기준이며 고객과 합의한 SLA가 아닙니다.

| 구분 | 목표·판정 | 확인 방법과 대응 |
| --- | --- | --- |
| 응답 속도 | 집계 p95 1초 이하 목표, 1초 초과 경고 | 요청 지표·로그를 확인하고 모델 준비·작업 부하를 조사 |
| 서버 오류 | 5xx 비율 1% 미만 목표, 1% 이상 경고 | 실패 경로·요청 ID로 원인 확인; 기존 정상 자료·모델 유지 |
| 생존·준비 | live와 ready를 분리 | live 성공만으로 예측 가능으로 보지 않음; ready 부족 사유 확인 |
| 모델 품질 | 초기 게이트·드리프트·후보 게이트를 각각 적용 | 아래 학습·감지·교체 정책에 따라 알림·재학습·평가·유지 |

서비스 경고는 `GroundwaterService.evaluate_service_health`에서 최근 300초 요청이 20건 이상일 때 판정합니다. 60초 주기로 확인하며 같은 UTC 분의 기록은 중복 생성하지 않습니다. 서비스 경고만으로 모델을 재학습하거나 자동 롤백하지 않습니다. 장애 복구는 아래 대응 절차에 따라 운영자가 확인합니다. 장기 가용성 목표의 측정·검증은 아직 완료하지 않았습니다.

## 학습과 초기 게이트

- 구별 residual LSTM: 32 → 32 → Dense 16 → 출력 1. 연속 20일의 수위·강수로 다음 날 수위를 계산합니다.
- gap-aware 시간 분할: 최근 유효 학습 정답 최대 730개, 검증 60일, 테스트 60일, 운영 재생 90일. 공백을 가로지르지 않고 scaler는 학습 구간만 사용합니다. strict 합성 검증 분할과 혼동하지 않습니다.
- seed 42, batch 32, 최대 100 epochs, early stopping patience 10. RMSE·MAE·표본 수와 persistence 기준을 기록합니다.
- 초기 허용: 검증 RMSE ≤ persistence 검증 RMSE × 1.10. 등록과 실제 champion 사용은 다릅니다. 실패 시 기존 모델을 유지하고 없으면 미준비로 표시합니다.

RMSE는 수위와 같은 단위로 오차를 비교할 수 있고 큰 오차를 강조합니다. 수위가 음수·0을 포함하므로 백분율 오차인 WAPE를 주 평가 지표로 직접 사용하지 않습니다. 실측과 합성 구간 지표를 합쳐 현장 성능으로 설명하지 않습니다.

## 감지 → 재학습 → 후보 평가

하루 진행은 t일 입력으로 t+1일 예측 저장 → t+1일 정답 공개 → 오차 평가 순서입니다. 같은 날짜의 중복 조회는 감지 표본을 늘리지 않습니다.

| 단계 | 현재 정책 |
| --- | --- |
| 감지 표본 | 동일 관측소·namespace·모델의 연속 정답 21일 |
| 임계값 | 초기 검증의 rolling 21일 RMSE P95 × 1.5, 계산 하한 1e-6 |
| 재학습 요청 | 임계값 연속 2회 초과, cooldown 21일, 최근 연속 41일 입력 확보 |
| 후보 학습 | 기존 모델 복제, 최근 41일·20일 문맥·21개 정답, scaler 유지, 10 epochs·LR 0.0001 |
| 후속 평가 | 후보 학습 뒤 새 정답 30일에서 기존과 같은 조건으로 비교 |
| 교체 게이트 | 후보 RMSE ≤ 기존 × 0.95, 과거 guard RMSE ≤ 초기 검증 × 1.10 |
| 대기·탈락 | 정답 부족은 평가 대기, 기준 미충족·날짜 공백은 기존 모델 유지 |

후보 평가 중 중복 후보를 만들지 않습니다. 모델 교체 뒤에는 새 버전의 오차 창을 다시 모읍니다. 감지는 예측 오차 증가이며 원인이나 현장 위험을 확정하지 않습니다.

파인튜닝 후보의 교체 함수에서도 저장된 평가 근거를 다시 확인합니다. 학습 이후 연속 30일의 같은 정답 구간, 후보·비교 모델 버전, 유한한 RMSE와 두 성능 기준을 확인하며, 미평가·평가 대기·탈락 후보는 직접 교체할 수 없습니다. 성능이 좋아져도 개선 폭이 5% 미만이면 기존 모델을 유지합니다. 후보 등록·평가만으로 서비스 모델이나 예측값이 바뀌지 않습니다.

평가 계산 이후와 교체 직전 시험 예측 이후에 현재 모델 버전을 다시 확인합니다. 비교한 기존 모델이 달라졌다면 `champion_changed`로 후보를 탈락시키고 최신 서비스 모델을 유지합니다. 교체 자격 확인과 전환은 구별 잠금 안에서 처리합니다. 이 잠금은 현재 단일 프로세스의 ModelManager 범위이며 여러 프로세스·외부 Registry 변경을 원자적으로 조율하는 분산 잠금은 아닙니다.

평가 지표·구간은 후보의 `shadow_result`에, 비교 기준 버전은 `parent_version`과 통과 평가의 `previous_version`에 보존합니다. 실제 전환은 champion·history와 함께 저장합니다. 확정된 탈락·교체 결과의 중복 평가는 같은 기록을 반환하며 재교체하지 않습니다. 새 후보는 이전 후보의 평가 결과를 상속하지 않습니다. 초기 학습은 persistence 비교 게이트, 파인튜닝은 후속·과거 성능 게이트, 명시적 롤백은 과거 승격 이력으로 각각 자격을 확인합니다.

## 시연·진행 표시

기본 상황은 추가 수위 변화가 없다는 뜻이며 경보가 절대 발생하지 않는다는 뜻은 아닙니다. 드리프트 시연은 별도 세션에서 첫 정답 22일째부터 수위에 +0.2를 더합니다. 예전 세션의 시작일·변화량은 보존합니다. 원본 CSV와 모델 출력·경보 결과는 조작하지 않습니다.

화면은 모델 준비·실제 처리 일수·재학습·평가 대기·실패를 표시합니다. 활성 작업의 조회는 3초, 일반 운영 조회는 30초 간격입니다. 외부 수집 주기가 아닙니다. 이미 선택한 상황은 이어서 사용하고 명시적 재시작 때만 새 기록을 만듭니다.

## 교체·복귀·장애 대응

모델을 로드하고 smoke 예측을 확인한 뒤 champion alias와 캐시를 교체합니다. 실패하면 기존 alias·캐시를 유지합니다. 실제 예측 응답의 model_version으로 새 모델 사용을 확인합니다.

이전 모델 복귀는 화면에서 사유 입력 없이 요청하며 API에는 고정 reason을 보냅니다. 실제 승격 이력이 있는 이전 검증 모델만 선택합니다. 작업 상태는 queued/running/completed/failed/interrupted이며 재기동 시 중단 작업은 자동 성공 처리하지 않습니다. 원인 확인 후 재시도하고 기존 실패 기록은 보존합니다.

모델 품질 이벤트는 OPEN → ACKNOWLEDGED → RESOLVED로 처리합니다. 외부 SMS·현장 점검 알림 발송은 구현 범위가 아닙니다. 서버 진단은 요청 ID·로그 → 준비 상태 → 작업·worker → 자료·모델 순서로 확인합니다. `/metrics/summary`의 p95 1초·5xx 비율 1%는 운영 목표이며 실측 결과는 증거에 따릅니다.

외부 수집은 승인 매핑·원천·단위·20일 입력·별도 모델을 갖춰야 합니다. 기본 화면과 별도 namespace를 사용하고 실패·부분 수집으로 정답을 만들지 않습니다. 상세 경로는 [API 명세서](contracts.md)과 자동 API 명세를 확인합니다. 과거 외부 원천·날짜 이동 공급 재생 설계는 archive의 기록입니다.

## 전국 실험 경로 `/api/v2`

전국 확장은 기존 지하수 관제 서비스의 같은 관측소 선택·상세·모델 관리 흐름에서 제공합니다. `NationalService`·전국 worker·`national_observed_v1`은 원천 계약이 다른 서울 모델·DB와 내부 이력을 분리합니다. 전국 강수 자료나 지하수 관측소 목록을 확보한 것, 관측소를 등록한 것, 그 관측소의 수위·강수·모델·발행 예측이 준비된 것은 각각 다른 상태입니다. 실제 확보·학습·연결 결과는 [실행 증거](../evidence/README.md)를 확인합니다. M2 강수 예보 입력과 호우특보 자동 수집은 아직 활성화하지 않았습니다.

### 자료·모델 준비

- 작업 실행은 `source_kind=observed`이며 `verified=true`인 관측소 또는 근거·매핑 버전이 있는 `source_contract_verified=true`, `mapping_status=experimental`, `operational_approved=false` 관측소에 허용합니다. 실험 작업 허용과 운영 승격 승인은 구분합니다. 단위·수위 기준면·근거를 확인해야 하며, registry 플래그 입력 자체가 외부 승인이나 단위 검증을 대신하지 않습니다. 합성 관측소를 등록할 수 있어도 전국 실측 학습·예측 작업에는 사용할 수 없습니다.
- 학습은 최신 연속 유효 구간을 선택합니다. 공백·충돌·다른 단위·기준면을 가로질러 연결하지 않으며, 구간이 짧으면 작업이 실패합니다. 예측에는 마감시각 이전에 공개되고 수집된 완전한 일자료 20일이 필요합니다.
- M0는 residual LSTM 32 → Dense 16 → 수위 변화량과 직전 수위 합산입니다. M1은 같은 20일 수위·강수 시계열에 예측 시점의 3/7/14일 누적강수·최대20일 연속강수일수·연중 날짜 sin/cos를 별도 벡터로 추가합니다. 20개 timestep마다 추가 14일 문맥을 붙이는 방식이 아니므로 동일 계약 파인튜닝은 41일을 유지합니다.
- scaler는 학습 구간에서만 적합합니다. 기본 분할은 최소 학습 정답 60개, tuning validation 30개, 별도 holdout 30개이며, 최소 140일이 필요합니다. validation 최소21개·holdout 최소30개를 지키며 요청에서 기간을 늘릴 수 있습니다. validation은 early stopping용이고 holdout은 학습·early stopping에 사용하지 않습니다.
- 최초 M0만 holdout RMSE ≤ 같은 날짜 persistence RMSE × 1.10이면 활성화할 수 있습니다. M1 최초 등록은 `baseline_required`이며 기존 M0가 필요합니다. 기존 활성 모델이 있으면 새 M0/M1을 등록해도 즉시 교체하지 않습니다.

### 감지·후보·발행 증거

전국 감지 임계값은 **최초 해당 모델 계열의 동결 holdout**에서 rolling21 RMSE P95 × 1.5, 하한 1e-6으로 산출합니다. 서울의 초기 validation 기준과 다릅니다. `initial_reference_version`으로 기준 모델을 보존하고 파인튜닝 때 최근 오차로 임계값을 다시 높이지 않습니다. `national_reference`에 기준 버전·정책·자료 해시를 저장합니다.

감시는 같은 관측소·namespace·활성 모델의 실제 발행 예측과 이후 공개된 정답으로 연속21일 RMSE를 매일 계산합니다. 최초 사용한 정답 revision을 보존하고 수정 자료로 기존 감지 근거를 조용히 덮어쓰지 않습니다. 날짜 공백은 연속 초과 횟수를 초기화하며 같은 날짜 재처리는 표본을 늘리지 않습니다. 임계값 연속2회 초과, cooldown21일 경과, 최근 연속 유효41일 확보, 평가 중 후보 없음이 모두 충족되면 작업을 등록합니다. 상태와 작업은 같은 SQLite transaction에서 기록합니다.

동일 계약 파인튜닝은 기존 모델·scaler를 유지해 20일 문맥과21개 새 정답으로 10 epochs·LR0.0001 학습합니다. 정답21개는 기존 학습·평가 자료의 마지막 날짜 이후여야 합니다. 모델 입력 계약을 바꾸는 M0→M1은 이 파인튜닝 경로가 아닌 새 초기학습으로 처리합니다.

후보 학습·초기 평가 cutoff 직후 **첫 연속30일**이 후속 평가 구간입니다. 두 모델은 같은 대상 날짜·입력 snapshot·발행시각으로 예측을 저장해야 하며, 발행시각은 정답 공개시각보다 앞서야 합니다. 기존 예측을 재조회한 뒤 후보가 당시 함께 발행된 것처럼 증거를 만들지 않습니다. 과거 자료 재예측만 있으면 `retrospective_evaluation`이고 교체할 수 없습니다. 일부 사전 발행 증거만 있으면 `awaiting_issued_predictions`로 남습니다.

전국 교체 게이트는 후속 RMSE5% 개선과 동결 holdout에서 동일 날짜 기존 모델 대비 RMSE 악화10% 이내입니다. holdout 정답이 비교 모델의 학습 정답과 겹치면 차단합니다. M1은 추가로 장마 RMSE5% 개선, 비장마·강한 강수 RMSE 악화10% 이내, 각 구간 정답 최소30개를 요구합니다. 강한 강수 기준은 학습 자료 일강수 P95로 동결하며 강수량0인 날은 강한 강수로 분류하지 않습니다. 장마 연도·지역 자료가 없으면 미분류로 남깁니다. 기본 holdout30일만으로 장마·비장마 각각30개를 채울 수 없으며, 표본이 부족하면 `insufficient_seasonal_evidence`로 대기합니다. 이 수치들은 추가 실험의 운영 가설이며 최적값·팀 합의 완료를 뜻하지 않습니다.

교체·복귀는 로딩·시험 예측을 먼저 확인하고 관측소별 파일 잠금과 활성 generation 비교 후 모델·scaler·입력 계약 묶음의 활성 참조를 변경합니다. 복귀는 이전 활성 이력에 있는 버전과 사유가 필요합니다. 이 잠금은 단일 호스트의 공유 로컬 볼륨 기준이며 분산 저장소·외부 다중 Registry 변경까지 보장하지 않습니다.

### 전국 worker의 자동 실행

`GROUNDWATCH_NATIONAL_SCHEDULER_ENABLED`는 기본 Compose에서 `true`입니다. worker 모듈을 직접 실행할 때 환경변수를 생략하면 `false`입니다. 수동 접수 작업을 처리하는 worker와 일별 자동 실행 활성화는 별개입니다. `true`이면 worker가 30초마다 확인하고 KST11:30 이후 검증된 실측 관측소의 발행 예측 감시·준비된 입력 예측·후보 평가를 순차 접수합니다. 자동 평가가 모든 게이트와 운영 승인 조건을 통과하면 교체합니다. 실험 모니터링 활성화는 운영 승인이나 승격 차단 해제를 뜻하지 않습니다. 관측소별 작업 scope와 일별 접수 기록으로 중복 작업을 막습니다.

최초 모델 학습·단위 승인·관측소 등록·외부 자료 자동 수집은 이 scheduler가 수행하지 않습니다. 키 부족·단위 미확인·자료 공백·입력 지연·모델 미준비 상태를 합성 자료나 추정값으로 대체하지 않습니다. 재기동 시 실행 중 작업은 `interrupted`로 남겨 명시적으로 재시도하며, 실패 이력을 성공으로 바꾸지 않습니다. `pipeline.monitor`와 작업 결과에서 감시 이유·cooldown·후보 대기·실패를 확인합니다.

### 별도 기상 관측 수집 worker

`backend.weather_worker`는 지하수 모델 scheduler와 분리한 기상청 API허브 관측 수집기입니다. `GROUNDWATCH_WEATHER_COLLECTION_ENABLED`는 기본 Compose에서 `true`이며, 모듈을 직접 실행하고 환경변수를 생략하면 `false`입니다. 실제 수집에는 서버의 `KMA_APIHUB_KEY`가 필요합니다. AWS 분자료의 지점·좌표 검증에는 `GROUNDWATCH_AWS_METADATA_PATH`를 사용하며 기본 파일은 `data/kma_station_metadata.csv`입니다. metadata가 없으면 분자료는 차단하고, 응답 자체에 지점 좌표가 있는 완료일 강수는 별도로 처리합니다. 이 worker가 지하수 관측소 매핑을 승인하거나 모델을 학습하지는 않습니다.

worker는30초마다 로컬 일정을 확인하지만 외부 요청은 AWS 분자료10분 간격, 완료일 강수는 KST11:30 이후 전일D-1에 하루1회입니다. 분자료는 현재 시각보다10분 앞선 완료 시각을10분 단위로 내림해 조회합니다. 요청·성공 checkpoint를 영속화하여 재기동 직후 중복 호출을 막고, 실패한 외부 요청은 최소10분 뒤 다시 시도합니다. 관측소별 요청을 수백 번 보내는 방식이 아니라 공식 전체 지점 응답을 한 번 수집합니다.

저장 경로는 `${GROUNDWATCH_STATE_DIR}/weather/`입니다. `national_aws_snapshot.json`은 최근 분자료 누적 강수, `national_aws_daily.json`은 완료된 일강수이며 서로 합치지 않습니다. 분자료의 `RN-DAY`는 진행 중 해당 날짜 누적값이므로 완료일 학습 정답·강수로 대체하지 않습니다. `raw/`에 기존 수집 함수가 비밀키를 제거한 원본과 해시를 보존하고, `archive/{snapshot|daily}/`에 요청 시각·날짜별 검증 결과를 저장합니다. 최신 JSON·archive·`weather_state.json`은 임시 파일에서 원자적으로 교체합니다.

공급자·파싱·단위·시각 검증이 실패하면 최신 정상 관측 파일을 유지하며 `weather_state.json`에 failed/blocked와 민감정보 없는 이유를 기록합니다. checkpoint가 collecting에서 중단된 경우도 재기동 backoff를 적용합니다. 화면·API는 정상 파일이 존재한다는 사실과 최신 수집 성공을 구분하고 observed_at·관측 날짜·collected_at·worker 상태를 함께 확인해야 합니다. 이 worker의 단위 테스트는 가짜 공급자·시계로 주기·재기동·실패 보존을 확인한 것이며, 실제 API 응답 성공은 별도 실행 증거로 기록합니다.

2026-10-08 별도 Compose 검증에서는 수집을 명시적으로 활성화해 실제 worker→원천→runtime 파일→HTTP 연결을 확인했습니다. `/api/v2/rainfall/collection-status`에서 AWS2026-10-08 18:10 분자료736개, 완료일2026-10-07 강수723개와 두 stream의 collected·전체ready 상태를 확인했습니다. 이 결과는 해당 검증 실행의 확보 상태입니다. 현재 기본 Compose는 수집 설정을 `true`로 전달하고, 직접 모듈 실행 시 환경변수 미지정 fallback은 `false`입니다. 지속 운영 SLA·지하수 모델 학습·전국 예측 성능을 입증한 결과는 아닙니다. API의 runtime 우선·bundled fallback·실패 시 last-good 유지도 가짜 공급자와 실제 router를 연결한 테스트로 별도 확인합니다.


### Compose와 직접 실행의 자동 기능 설정

팀 공용 실행 기준은 루트 `docker compose up --build`입니다. 기존 지하수 관제를 전국 관측소로 확장한 하나의 서비스이며, 수집·학습·감시 프로세스는 내부 책임을 나누어 실행합니다.

| 환경변수 | 기본 Compose | 환경변수 없이 모듈 직접 실행 | 기능 |
|---|---|---|---|
| `GROUNDWATCH_WEATHER_COLLECTION_ENABLED` | true | false | 기상청 분자료·완료일 강수 수집 |
| `GROUNDWATCH_NATIONAL_OBSERVATION_COLLECTION_ENABLED` | true | false | 명시적 등록 매핑의 전날 수위·강수 결합 수집 |
| `GROUNDWATCH_NATIONAL_SCHEDULER_ENABLED` | true | false | 준비된 관측소의 일별 모델 작업 접수 |
| `GROUNDWATCH_EXPERIMENTAL_MODELS_ENABLED` | true | false | 확보된 공식 실험 결합 자료로 초기 모델 준비 |
| `GROUNDWATCH_EXPERIMENTAL_MONITORING_ENABLED` | true | false | 명시적 실험 매핑의 발행 예측 감시 허용 |

`.env`에서 false를 명시하면 Compose의 해당 기본값을 덮어씁니다. 설정 true와 실제 수집·학습 성공은 구분합니다. 키 부족·자료 미확보·입력 지연·모델 게이트 실패에서는 상태와 기존 정상 자료를 유지하며, 미등록 관측소를 자동 승인하거나 합성 관측으로 대신하지 않습니다. 실험 모니터링을 켜도 `operational_approved=false` 모델의 운영 승격은 허용하지 않습니다.

## 전국 후보 종료와 메모리 관리

M1의 동결 계절 검증 구간에 필수 장마·비장마·강한 강수 정답30개가 없으면 `expired_insufficient_seasonal_evidence`로 후보를 종료합니다. 그 외 후속 정답·발행 근거가 부족한 후보는 기본90일 이후 `expired_shadow_timeout`으로 종료합니다. 기존 모델을 유지하고 종료 이유·후보 이력을 보존하며, 종료된 후보는 중복 후보 대기에서 제외합니다. 새 후보도30일·RMSE5%·과거 악화10%의 원래 조건을 따릅니다.

TensorFlow 작업은 상태 디렉터리의 공통 파일 잠금으로 한 번에 하나씩 실행합니다. worker는 작업마다 하위 프로세스를 새로 만들고 종료하며, 다년 평가는 모델별 결과를 저장합니다. 비정상 종료 작업은 `interrupted`로 보존하고 자동 재학습하지 않습니다. 실패·중단 작업만 재요청 API로 명시적으로 재접수합니다. 이전 계절 보고는 해시별로 보존합니다. 기존 데이터 볼륨을 삭제해 복구하지 않습니다.

전국 합성 자료는 별도 namespace와 출처로 관리하며 실제 운영 승격을 차단합니다. 합성 장마6/20~7/25는 시나리오 분류이고 공식 장마 통계가 아닙니다. 최신 개발 검증과 실제 운영 승인 범위는 [실행 근거](../evidence/README.md)를 확인합니다.


## 실제 API 학습과 초기 게이트

- `api_native_masked_v1`의 구별 masked residual LSTM을 사용합니다. 입력은 연속 20일 수위·강수·강수 결측 표시이며 다음 날 실제 수위가 정답입니다. 날짜 공백을 가로지르지 않습니다.
- 최소 유효 정답 윈도우 50개가 필요합니다. 전체 유효 윈도우를 시간순으로 약 60% 학습·20% 검증·20% 시험으로 나누며 검증·시험은 각각 최소 10개입니다. 결측일 때문에 비율과 달력 기간이 같지는 않습니다.
- 강수 중앙값과 scaler는 학습 구간에서만 계산하고 이후 고정합니다. 원자료의 null·수위 원값·부호를 보존하며 모델 입력에서만 대체합니다.
- seed 42, batch 32, 최대 100 epochs, early stopping patience 10, LR 0.0001. 초기 허용은 검증 RMSE ≤ 전일 수위 유지(persistence) RMSE × 1.10입니다.
- 새 feed가 들어오면 미준비 모델만 초기 학습하고 기존 champion은 재사용해 새 입력으로 예측합니다. 매일 전체 모델을 재학습하지 않습니다. 자동 재학습은 아래 드리프트 정책을 따릅니다.

RMSE·MAE는 API 원값 단위이며 물리적 수위 단위가 검증됐다는 뜻은 아닙니다. 검증 게이트 통과가 시험 구간에서 persistence보다 우수하다는 보장은 아닙니다. 후보 평가 후 모델의 metrics에는 후속 평가·guard 지표가 표시될 수 있습니다.


## 실제 API 감지 → 재학습 → 후보 평가

예측 발행 당시 정답이 없었던 대상 날짜만 저장합니다. 이후 API 수집에서 정답이 도착하면 최초 수신 정답으로 평가를 고정합니다. 과거 시험 구간 예측·중복 조회·같은 입력으로 재발행한 예측은 감지 표본을 늘리지 않습니다. 공급자가 날짜를 건너뛰어 제공하면 연속 표본 조건을 충족할 때까지 기다립니다.

| 단계 | 실제 API 정책 |
| --- | --- |
| 감지 표본 | 같은 관측소·namespace·현재 모델의 연속 정답 21일 |
| 임계값 | 초기 검증 RMSE × 1.5. 기존 시연의 rolling P95 정책과 다름 |
| 재학습 요청 | 임계값 연속 2회 초과, cooldown 21일. 후보·활성 모델 작업 중복 방지 |
| 후보 학습 | 최신 연속 41일·21개 정답, 기존 모델 복제·scaler/강수 대체값 유지, 최대 30 epochs·LR 0.0001 |
| 후속 평가 | 후보 학습 종료 다음 날부터 정확히 연속 달력 30일 정답. 빠진 날짜를 더 늦은 날짜로 대신하지 않음 |
| 교체 게이트 | 같은 30일의 후보 RMSE ≤ 기존 × 0.95, 미학습 과거 guard에서 후보 RMSE ≤ 같은 기존 모델 × 1.10 |
| guard | 부모 모델의 검증 구간 또는 상속된 guard 중 후보 학습 정답보다 앞선 최소 10개 정답 |
| 대기·탈락 | 정답 부족은 대기, 게이트 미충족은 기존 유지. 학습·로드 실패는 작업 실패와 기존 모델 유지 |

외부 worker는 60초마다 수집·학습·감시 조건을 확인합니다. 감시·재학습·평가·교체는 하나의 학습 worker에서 영속 작업으로 직렬 실행합니다. 입력 스냅샷·예측·평가·경보·작업·모델 버전을 보존하고, 재시작이나 작업 재시도로 같은 경보·후보를 중복 생성하지 않습니다. 교체 후 새 버전의 오차 창을 다시 모읍니다. 실제 운영에 새 정답이 없으면 중간 단계가 대기인 것이 정상입니다.


## 실제 API 관측 feed

`GROUNDWATCH_COLLECTION_ENABLED=true`일 때 KST 10시 이후 하루 1회 자동 수집합니다. 오류가 있으면 마지막 점검 1시간 후 재시도하며 worker는 60초마다 조건을 확인합니다. 90일 자료에서 365일로 확대하는 초기 보충 수집도 허용합니다. ‘하루 1회’는 수집 배치 기준이며 서울시·기상청 페이지 요청은 여러 번입니다. 화면 수동 수집은 이 일정과 별도로 접수할 수 있습니다.

서울시 관측소·날짜 필터가 실응답에서 적용되지 않아 전체 응답을 페이지 단위로 검증해 고정 관측소 이름으로 추출합니다. 최신 유효 지하수 관측 기준 365일, 최대 120페이지이며 각 페이지는 1,000행입니다. 기상청은 날짜 범위의 ASOS 108 자료를 100행씩 요청합니다. 미래 관측을 제외하고 건수·정렬·페이지 완전성을 검사하며 실패한 원천은 이전 성공 자료와 오류 상태를 유지합니다. 모든 관측소의 365일 완전 관측을 보장하는 설정은 아닙니다.

원본 JSON·latest.json·학습/발행 입력 스냅샷·models.json은 `runtime/groundwatch/external/feed/`, 모델은 `models/api_native_masked_v1/`, 발행 예측·평가·감시·모델 작업은 팀 상태 DB에 저장합니다. 수동 수집 작업은 별도 외부 수집 DB에 있으므로 `/api-observations/collection-jobs`로 조회합니다.

2026-10-08 검증에서 최신 지하수 관측은 2026-08-31이고 25곳 예측이 준비됐습니다. 대부분 예측 대상은 2026-09-01이며 노원구는 관측 2026-07-31·예측 2026-08-01입니다. 관측일을 수집일이나 오늘로 바꾸지 않습니다. 실제 새 정답이 쌓이기 전의 대기는 서비스 실패나 드리프트 미구현을 의미하지 않습니다.

실제 API 후보 승격도 저장된 관측 스냅샷을 다시 읽어 같은30일·부모 버전·동결 guard의 RMSE를 재계산합니다. pass 플래그나 누락/변조된 평가 수치만으로 활성화하지 않습니다.

## 실행 문제 해결

<details>
<summary>실행 오류별 확인 방법과 해결 절차</summary>

#### Docker 연결 오류로 시작되지 않을 때

`Cannot connect to the Docker daemon` 오류가 나오면 Docker Desktop을 실행하고 엔진 준비가 끝날 때까지 기다린 뒤 다시 실행합니다.

```bash
docker compose up --build
```

#### 이전 버전의 컨테이너가 남아 있을 때

이전 `serving-app` 서비스에서 최신 `backend` 서비스로 갱신할 때 기존 컨테이너가 포트를 사용하고 있으면 저장소 루트에서 먼저 종료합니다. 같은 Compose 프로젝트의 이전 서비스도 정리하며 모델·자료 볼륨은 유지합니다.

```bash
docker compose down --remove-orphans
docker compose up --build
```

#### 8100 포트가 이미 사용 중일 때

`port is already allocated` 또는 `address already in use` 오류가 나오면 로컬 `.env`에 빈 포트를 지정합니다. 기존 설정은 유지하고 아래 항목만 추가하거나 수정합니다.

```dotenv
GROUNDWATCH_PORT=8101
```

다시 `docker compose up --build`를 실행한 뒤 http://localhost:8101/에 접속합니다. API 명세와 헬스체크 주소도 같은 포트를 사용합니다.

#### 패키지 다운로드 오류로 이미지 빌드가 실패할 때

`npm ci` 또는 `pip install` 단계에서 연결 오류·시간 초과가 나오면 인터넷 연결과 Docker의 프록시 설정을 확인한 뒤 빌드를 다시 실행합니다. 빌드 로그에서 실패한 패키지와 오류를 확인하며, 프로젝트 의존성 버전을 임의로 바꾸지 않습니다.

```bash
docker compose build backend
```

빌드가 성공하면 `docker compose up`으로 시작합니다.

#### 화면이 열리지 않거나 컨테이너가 종료될 때

다음 명령으로 컨테이너 상태와 오류를 확인합니다.

```bash
docker compose ps -a
docker compose logs --tail=100 backend
```

- 컨테이너가 실행 중이면 `.env`의 포트와 접속 주소가 같은지 확인합니다.
- 종료 원인이 설정·API 연결 오류라면 해당 설정을 수정하고 `docker compose up --build`를 다시 실행합니다.
- `OOMKilled` 또는 메모리 부족이 확인되면 Docker Desktop의 메모리 할당을 늘리고 다시 실행합니다.
- 자료·모델 검증 오류라면 로그에 표시된 파일과 원인을 확인합니다. 실행 자료를 삭제하거나 결측값을 임의로 채워서 우회하지 않습니다.

#### 화면은 열리지만 예측이 나오지 않을 때

첫 실행에서는 자료 검증과 모델 학습이 끝날 때까지 기다립니다. ‘모델 관리’에서 작업 상태를 확인하고, 실패·중단 작업은 오류 원인을 해결한 뒤 ‘다시 요청’을 누릅니다.

입력 자료가 부족하거나 초기 성능 평가를 통과하지 못한 경우에는 재시작만으로 해결되지 않습니다. 화면의 미준비 사유를 확인하고 필요한 연속 관측 자료를 확보해야 합니다. 저장 자료를 확인하려면 조회 모드를 ‘저장 자료로 검증’으로 바꾸고 확보된 날짜를 선택합니다.

#### `/health/ready`가 503이거나 `STALE`이 표시될 때

마지막 관측일과 모델 입력 종료일을 확인합니다. 오래된 자료가 원인이면 외부 수집 키·활용 승인을 확인하고 최신 자료를 수집합니다. 모델이 미준비라면 ‘모델 관리’에서 학습 작업과 평가 결과를 확인합니다.

`/health/live`가 200이면 API 프로세스는 살아 있습니다. 준비 상태 503을 없애기 위해 자료 날짜나 상태 값을 임의로 바꾸지 않습니다. 공급자가 최신 자료를 제공하지 않으면 확보된 자료를 조회하면서 갱신을 기다려야 합니다.

#### 서울 실제 API 관측이 0곳이거나 수집이 실패할 때

로컬 `.env`의 `SEOUL_OPEN_DATA_KEY`·`KMA_ASOS_SERVICE_KEY`와 각 서비스의 활용 승인 상태를 확인합니다. 키를 수정했다면 컨테이너에 설정을 다시 반영합니다.

```bash
docker compose up --build
```

‘서울 실제 API 관측·예측’ 모드에서 수동 수집을 요청하고 수집 작업의 완료·실패 사유를 확인합니다. 전국 기상·지하수 수집도 해당 키와 승인을 확인합니다. 공급자 오류·자료 없음은 키 오류와 구분하며, 수집 실패 중에는 기본 저장 자료를 조회할 수 있습니다.

오류가 계속되면 팀에 **실행 명령·오류 메시지·컨테이너 상태·발생 시각**을 공유합니다. 로그를 전달하기 전에 API 키·토큰을 가립니다. 모델과 이력이 저장된 볼륨은 유지합니다.
