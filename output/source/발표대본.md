# GroundWatch 발표 대본

최신 통합 서비스와 37쪽 발표자료 기준입니다. 본문 1~19쪽과 29~36쪽을 중심으로 설명하고, 20~28쪽은 합성 교체 시연의 증거 부록으로 선택해 사용합니다. 전체 페이지를 읽으면 약 20~25분이며 10분 발표에서는 부록을 생략합니다.

## 1쪽 · GroundWatch

안녕하세요. 광주3반 5조 발표를 맡은 한형준입니다. GroundWatch는 서울 25개 구별 대표 관측소의 수위·강수를 기본 화면에 제공합니다. 구 전체 평균은 아닙니다. 서울 추가 실측은9월30일까지 확보했고 이후 합성 확장을 명확히 구분합니다. 추가 실측 조회가 기존 모델의 재평가나 승격 완료를 뜻하지는 않습니다. 전국 실측 3곳의 280일 자료와 장마 평가는 추가 조회이고 운영 미승인입니다. 입력 마지막 날의 1일 뒤 수위를 추정하며, 발행 시점에 따라 당일 추정과 다음 날 예측을 구분합니다. 오늘은 운영 기준과 실제 동작 결과를 설명하겠습니다.

## 2쪽 · 예측을 확인하는 담당자와 품질을 지키는 운영자

제안 B2B 고객은 지하수 관측·시설 유지관리 업무를 수행하는 기업의 운영 담당자입니다. 업무 담당자는 수위·강수·입력 날짜와 모델 품질을 함께 확인하고, 모델 운영자는 오차 증가와 재학습·교체 근거를 관리합니다. 공공기관은 자료 제공·현장 검증 협업 대상이며 공공기관 직접 판매는 B2G입니다. B2G가 과제 B2B 조건으로 인정됐다고 주장하지 않으며 실제 고객 도입·계약·매출·현장 효과는 아직 검증하지 않았습니다.

## 3쪽 · 장애·지연·품질 저하가 판단에 미치는 영향

장애가 나면 담당자는 예측을 조회할 수 없습니다. 응답이 늦으면 여러 관측소를 확인하고 비교하는 업무가 지연됩니다. 모델 품질이 나빠지면 오차가 커진 예측을 계속 업무에 참고할 수 있습니다. 이 문제들이 서로 다르기 때문에 생존·준비 상태, 응답 지표, 모델 오차를 나누어 감시하도록 설계했습니다. 이는 저희가 정의한 업무 시나리오이며 현장 고객 효과를 측정한 결과는 아닙니다.

## 4쪽 · 수업 파이프라인의 GroundWatch 도메인 매핑

가이드의 도메인 매핑표를 기준으로 여덟 항목을 바꿨습니다. 예측 대상은 종가에서 다음 날 지하수위로, 입력은 20일 수위와 강수로 치환했습니다. 고정 금액으로 판단하던 게이트는 기존 예측 방식과의 상대 오차 비교로 바꿨습니다. 재학습과 알림의 흐름은 유지하면서 관측소, 날짜, 단위, 모델 버전으로 기록을 연결했습니다. 다음부터는 이렇게 바꾼 기준이 어떤 서비스 범위를 만드는지 설명하겠습니다.

## 5쪽 · 예측 품질과 현장 안전 판단의 경계

현재 확인할 수 있는 결과는 관측소별 다음 날 수위 예측과 모델 운영 상태입니다. 기본 시연 자료에는 공식 과거 관측과 별도로 구분한 합성 확장이 포함됩니다. 현장 적용을 위해서는 관측소의 적합성과 수위 변화의 원인, 실제 업무 시간이나 비용 효과를 추가로 검증해야 합니다. 싱크홀 발생 확률이나 안전 등급을 산출했다고 설명하지 않습니다. B2B는 관측·시설 유지관리 기업에 제안하고 공공기관은 협업 대상으로 구분합니다. 도입·계약·매출 실적은 확인하지 않았습니다.

## 6쪽 · 다음 날 수위 예측을 품질 감시까지 연결

최근 연속 20일의 수위와 강수를 관측소별 모델에 입력합니다. 모델은 LSTM으로 다음 날의 변화량을 예측하고 마지막 입력 수위에 더합니다. 관측소마다 모델과 scaler를 따로 관리하며 scaler는 학습 구간만 보고 학습합니다. 예측 결과에는 대상 날짜와 모델 버전을 함께 남겨 이후 실제 관측값이 들어왔을 때 같은 날짜의 오차를 계산할 수 있게 했습니다.

## 7쪽 · 운영 목표와 측정 결과

응답 목표는 p95 1초 이하입니다. p95는 요청 시간의 95백분위로, 일부 느린 요청까지 살피기 위한 지표입니다. 저장된 300초, 107개 요청의 측정에서는 0.6538초였고 서버 오류인 5xx는 0건이었습니다. 이 수치는 해당 요청 창의 결과이며 장기간 가용성을 보장하는 SLA는 아닙니다. 초기 실제 관측 모델은 종로구 검증 RMSE 0.032519로, 직전 수위를 그대로 예측하는 persistence 기준의 허용 상한 0.037465를 통과했습니다. 수위에는 음수와 0이 있어 백분율 오차보다 같은 수위 단위의 RMSE를 중심으로 설명합니다.

## 8쪽 · AIOps가 만든 변화: 개선한 후보만 교체

[두 시연의 막대를 각각 가리킨다.]

AIOps의 가치는 새 모델을 만들었다는 사실보다, 실제로 나아졌는지 확인하고 교체를 결정한 결과로 보여드리겠습니다. 이번 합성 시연에서 같은 후속 정답 30일을 비교했을 때 기존 RMSE는 0.0232006, 후보는 0.0210489로 9.27% 감소했습니다. 과거 구간 검사도 통과해 v2로 교체했습니다. 반면 다른 시연의 후보는 2.51% 개선되어 5% 기준에 미달했고 기존 모델을 유지했습니다. 그래프는 각 시연의 기존 오차를 100으로 맞춘 것으로, 서로 다른 시연의 후보를 직접 비교하는 그래프는 아닙니다. 현장 비용 절감이나 사고 예방 수치는 아직 측정하지 않았습니다.

## 9쪽 · 드리프트가 생길 수 있는 상황

장마나 장기 가뭄은 강수와 지하수위의 관계를 학습 때와 다르게 만들 수 있습니다. 양수나 배수 조건이 바뀌면 강수만으로 설명하기 어려운 수위 변화가 나타날 수 있습니다. 센서 교체나 영점 보정은 측정 기준의 변화를 일으킬 수 있습니다. 이런 상황에서는 먼저 원자료, 단위, 관측 조건을 확인해야 합니다. 현재 시스템은 이 원인들을 분류하는 기능 대신 실제 정답에 대한 예측 오차 증가를 감지합니다. 시연에서는 첫 정답 22일째부터 수위에 0.2를 더해 이러한 변화를 재현했습니다.

## 10쪽 · 배포 전에 입력과 성능 회귀를 차단

서울 기존 모델은 초기 검증 구간, 전국 모델은 동결한 holdout 구간을 기준으로 guard와 오차 임계값을 계산합니다.

모델을 배포하기 전에 입력과 성능을 차례로 검사합니다. 입력은 연속 20일인지, 관측소와 날짜·단위가 맞는지, 강수가 0 이상인지 확인합니다. 초기 모델은 persistence 검증 RMSE의 110% 이내여야 합니다. 재학습 후보는 학습 이후 새로 확보한 정답 30일에서 기존 모델보다 오차가 5% 이상 줄어야 하고, 과거 검증 구간도 110% 허용 범위를 통과해야 합니다. 마지막으로 모델 로드와 시험 예측이 성공해야 서빙 모델을 바꿉니다.

## 11쪽 · 모니터링 지표·임계값과 설계 근거

서울 기존 모델은 초기 검증 구간, 전국 모델은 동결한 holdout 구간을 기준으로 guard와 오차 임계값을 계산합니다.

서비스와 모델을 각각 감시합니다. 서비스는 300초에 최소 20요청이 모였을 때 p95가 1초를 넘거나 5xx 비율이 1% 이상이면 이벤트를 기록합니다. 모델은 21일 RMSE를 사용하고 정상 검증 구간의 rolling RMSE 95백분위에 1.5배를 곱한 값을 임계로 사용합니다. 단발 초과에 반응하지 않도록 연속 2회 조건을 두고, 중복 재학습을 줄이기 위해 21일 cooldown을 적용했습니다. 이 값들은 과제의 운영 정책이며 지반 안전 기준은 아닙니다.

## 12쪽 · 드리프트 대응 순서

[왼쪽부터 오른쪽으로 순서대로 가리킨다.]

정답이 쌓이면 오차를 감시하고, 반복 초과 시 품질 알림과 재학습 작업을 남깁니다. 최근 41일에는 입력 문맥 20일과 학습 정답 21일이 들어갑니다. 후보를 만든 뒤에는 새로운 정답 30일을 기다려 기존 모델과 비교합니다. 개선과 회귀 검사에 모두 통과하면 교체하고 실패하면 기존 모델을 유지합니다. 따라서 재학습 완료와 모델 교체는 서로 다른 단계입니다.

## 13쪽 · 실패·대기·복귀도 운영 결과로 남김

정답이 부족하면 평가를 기다립니다. 후보가 성능 기준에 미달하거나 입력 날짜에 공백이 있으면 기존 모델을 유지합니다. 모델 로드 실패도 전환을 중단하고 오류를 기록합니다. 이미 검증한 이전 모델로 돌아갈 때는 사유를 남기는 복귀 요청을 사용합니다. 프로세스가 재시작되어 중단된 작업도 성공으로 처리하지 않고 interrupted로 보존합니다. 이처럼 무엇을 바꾸지 않았는지와 그 이유까지 운영 이력에 남깁니다.

## 14쪽 · GroundWatch 구현 구성

[위쪽 데이터 흐름을 왼쪽부터 읽는다.]

자료를 업로드하면 FastAPI가 형식을 검사하고 worker가 모델을 학습합니다. 학습 결과와 지표·버전은 MLflow에 등록하고 FastAPI가 검증된 모델로 추론합니다. 예측과 운영 기록은 SQLite에 저장합니다. 이 구성은 단일 serving-app 컨테이너 안에서 실행합니다. MLflow는 로컬 SQLite와 artifact 파일을 사용하므로 별도 MLflow 서버를 띄운 구조는 아닙니다. 대시보드는 서빙 API를 호출하고 자료와 모델, 운영 이력은 볼륨으로 보존합니다.

## 15쪽 · 예측 기록에서 재학습 트리거까지

이번에는 운영 중 데이터가 흐르는 순서입니다. 먼저 예측값과 모델 버전·대상일을 저장합니다. 그 날짜의 실제 정답이 도착하면 예측과 연결해 오차를 계산합니다. 반복된 오차 증가를 감지하면 이벤트와 로그를 남기고 worker의 재학습 작업을 등록합니다. 이후 후보 검증과 교체는 앞서 설명한 운영 정책을 따릅니다.

## 16쪽 · 화면과 시연이 실제 호출하는 API

실제 사용되는 API를 기능별로 모았습니다. 추론은 POST, 생존과 준비 확인은 GET입니다. 업로드와 학습, 자료 진행, 복귀는 비동기 작업으로 접수합니다. 여기서 202는 요청을 받았다는 뜻이며 완료 여부는 작업 조회에서 다시 확인합니다. 순차 배치 검증에는 replays의 advance를 사용합니다. 교수자 원본의 batch-test나 logs 주소를 팀 서비스의 엔드포인트로 옮겨 적지 않았습니다.

## 17쪽 · Swagger 계약과 실제 200·422 응답

왼쪽은 실제 20일 요청 중 한 행입니다. 관측소, 날짜, 수위, 강수와 수위 단위를 보냅니다. 정상 응답에는 예측값뿐 아니라 사용 모델 버전과 입력·예측 날짜가 함께 있습니다. 빈 sequence를 보낸 실제 요청은 422와 too_short 오류를 반환했습니다. 따라서 잘못된 입력을 받아 임의의 예측값을 만드는 대신 계약 단계에서 막는 것을 확인했습니다.

## 18쪽 · 업로드·학습·배치 요청 예시

자료 업로드는 관측 CSV와 관측소·단위 manifest를 함께 전송합니다. 학습에는 자료 식별자와 대상 구를 보냅니다. 배치 검증은 진행할 일수를 보내며 새 정답을 순서대로 공개하고 감시·후보 평가까지 실행합니다. 표의 식별자는 계약을 설명하기 위한 예시이며 실제 요청과 응답은 증거 파일에 보존했습니다. 접수 결과로 받은 작업 식별자를 조회해 최종 상태와 오류를 확인합니다.

## 19쪽 · 헬스·로그 조회와 오류 예시

live는 프로세스 생존, ready는 입력과 모델의 준비를 확인합니다. 준비가 부족하면 ready는 503을 반환합니다. events와 jobs에서는 품질 이벤트와 작업의 상태·오류를 조회합니다. 실제 시연에서도 초기 모델 준비가 끝나기 전에 자료 진행을 요청했을 때 409가 반환되어, 준비되지 않은 상태의 진행을 막는 것을 확인했습니다. 이제부터는 이렇게 호출한 결과를 실제 화면으로 보여드리겠습니다.

## 발표자 참고 · 질의응답과 근거

- **현장 효과를 숫자로 물으면:** 합성 시연의 RMSE 9.274457% 감소와 기준 미달 후보의 교체 차단까지 확인했습니다. 업무 시간·비용·사고 감소는 측정하지 않았습니다.
